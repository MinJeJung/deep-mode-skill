# 깊게 (심층 모드)

사용법: `/깊게 <원래 요청>` · 진행 전에 확인을 받으려면 `/깊게 --확인 <원래 요청>`

인자에 원래 요청이 없으면 직전 대화의 사용자 요청을 원래 요청으로 삼는다. 그것도 없으면 무엇을 할지 한 번만 묻는다.

이 파일 끝에 부록 3개가 있다. 부록 A는 작업 유형별 5문항 답 기준, 부록 B는 1~4단계 출력 템플릿, 부록 C는 적용 예시다. 1단계 전에 부록 A에서 해당 유형 절만 읽는다.

## 1단계: 사전 질문 5개 (항목당 3줄 이내)

먼저 작업 유형을 한 줄로 밝힌다 (판별표: 부록 A).

1. **전문가 관점**: 이 분야 최고의 전문가라면 사용자가 요청하지 않았어도 반드시 했을 일은?
2. **원자료**: 어떤 1차 자료·원본 데이터부터 확인해야 하나? (어디에 있는지까지)
3. **방법론·도구**: 가장 적합한 방법과 도구는? 배제한 대안과 그 이유도 한 줄로.
4. **객관적 검증**: 너와 사용자의 판단이 아니라 결과를 검증해 줄 외부 기준은? (공식 문서, 실행 결과, 원데이터 대조, 독립 검토자 등)
5. **완료 기준**: 무엇이 확인되면 이 작업이 끝난 것인가?

답은 일반론이 아니라 이번 요청에 맞춘 구체적인 내용이어야 한다. 실제 사용 가능한 도구·파일·출처를 이름으로 적는다.

## 2단계: 프롬프트 다시 쓰기

1단계 답을 반영해 원래 요청을 더 깊고 구체적인 프롬프트로 다시 써서 코드 블록으로 보여 준다. 다음을 담는다.

- 목표와 산출물 형식·저장 위치
- 먼저 확인할 원자료
- 사용할 방법과 도구
- 실행할 검증 절차
- 완료 기준

## 3단계: 실행

- `--확인`이 있거나, 작업이 비용이 크거나(유료 API, 대량 배치) 외부에 영향을 주는 경우(발송·게시·제출): 다시 쓴 프롬프트를 보여 준 뒤 멈추고 사용자 확인을 기다린다.
- 그 밖에는 확인 없이 다시 쓴 프롬프트대로 바로 작업한다.
- 원래 요청의 범위를 넘어서는 일은 하지 않고 "발견 사항"으로 제안만 한다.

## 4단계: 검증과 보고

- 4번에서 정한 검증을 **실제로 실행**한다. 말로만 "검증 가능하다"고 쓰지 않는다.
- 보고 순서: ① 결과 ② 실행한 검증과 그 결과(명령, 열어 본 파일·화면, 대조한 출처) ③ 5번 완료 기준 충족 여부(항목별 충족/미충족) ④ 검증하지 못한 항목과 이유.
- 검증이 실패하거나 완료 기준을 못 채웠으면 완료라고 쓰지 않는다.

# 부록 A. 작업 유형별 5문항 답 기준

1단계 답을 쓸 때 작업 유형에 맞는 행을 골라 출발점으로 삼는다. 표의 내용을 그대로 옮기지 말고 이번 요청에 맞게 구체화한다 (파일명·출처명·명령을 이름으로 적는다).

### 유형 판별

| 유형 | 신호 |
|---|---|
| 리서치·팩트체크 | "조사해줘", "최신 동향", "사실이야?", 수치·날짜·인용 확인 |
| 보고서·문서 | 보고서, 제안서, 칼럼, 블로그 원고, 정리 노트 |
| 데이터 분석 | xlsx·csv, 정산, 통계, 추이, 비교 |
| 강의안·교육 자료 | 강의, 커리큘럼, 실습 문제, 슬라이드 |
| 자동화·시스템 설계 | n8n, 스크립트, 스킬·에이전트 설계, 파이프라인 |
| 코드 변경 | 버그 수정, 기능 추가, 리팩터링 |

여러 유형이 섞이면 산출물 기준으로 주 유형 하나를 정하고 나머지는 보조로 쓴다.

### 리서치·팩트체크

1. **전문가 관점**: 주장마다 1차 출처를 따로 확인한다. 발표일과 보도일을 구분한다. 반대 근거도 찾는다.
2. **원자료**: 영어권 1차 소스(공식 발표, 논문, 기업 문서)를 먼저 본다. 한국 자료는 국내 맥락용이다.
3. **방법론·도구**: 브라우저로 원문 페이지를 직접 읽는다. 페이지가 많으면 리서치용 하위 에이전트에 맡긴다. 배제: 검색 도구 요약본만 쓰기 (날짜·수치가 왜곡될 수 있음).
4. **객관적 검증**: 별도 팩트체크 에이전트나 검토자가 출처를 독립적으로 다시 찾아 대조. 소스 유형 3종(뉴스·논문/리포트·현업 반응) 교차.
5. **완료 기준**: 핵심 주장마다 출처 URL과 확인 날짜가 붙어 있다. 미확인 주장은 "미확인"으로 표시되어 있다.

### 보고서·문서

1. **전문가 관점**: 독자와 그 독자가 내릴 결정을 먼저 정한다. 결론을 첫 문단에 둔다.
2. **원자료**: 사용자가 준 원본 파일, 관련 노트, 이전 버전 산출물.
3. **방법론·도구**: 형식에 맞는 문서 스킬 (docx·pptx·xlsx 등). 사용자 이름으로 나가는 글이면 사용자 문체 규칙을 적용.
4. **객관적 검증**: 렌더링한 실제 파일을 열어 확인한다. 사실 주장은 팩트체크. 필요하면 다른 모델로 교차 검토.
5. **완료 기준**: 정해진 위치에 파일이 저장되어 있다. 파일이 열린다. 요청한 분량·항목이 다 들어 있다.

### 데이터 분석

1. **전문가 관점**: 원데이터의 행 수, 기간, 결측값, 중복을 먼저 확인한다. 집계 전에 단위를 맞춘다.
2. **원자료**: 원본 xlsx·csv, API 응답, 대시보드 export. 가공본보다 원본을 우선한다.
3. **방법론·도구**: Python 또는 스프레드시트 도구. 수치는 코드로 다시 계산해 검산한다. 배제: 눈대중 합계.
4. **객관적 검증**: 원데이터 합계와 결과 합계 대조. 표본 3건을 원본에서 직접 찾아 값 비교.
5. **완료 기준**: 합계가 원데이터와 일치한다. 가정과 제외한 데이터가 보고서에 적혀 있다.

### 강의안·교육 자료

1. **전문가 관점**: 학습 목표를 행동 동사로 정한다. 실습이 실제로 실행되는지 직접 해 본다.
2. **원자료**: 도구 공식 문서, 교육 기관 요구사항, 이전 강의 자료와 수강생 피드백.
3. **방법론·도구**: 커리큘럼·실습 문제·슬라이드 제작 도구. 배제: 공식 문서 없이 기억으로 기능 설명.
4. **객관적 검증**: 실습 단계를 현재 버전 도구에서 직접 실행한 결과. 기능·가격·한도는 공식 문서 대조.
5. **완료 기준**: 차시별 목표·실습·소요 시간이 있다. 모든 실습이 실행 확인되었다.

### 자동화·시스템 설계

1. **전문가 관점**: 실패 경로(인증 만료, 빈 입력, 중복 실행, 재시도)를 먼저 설계한다. 되돌리는 방법을 정한다.
2. **원자료**: 기존 워크플로·스크립트 원본, API 공식 문서, 로그. 가능하면 화면 대신 API로 읽는다.
3. **방법론·도구**: 기존 도구 확장을 우선한다. 새 도구는 이유를 적는다. 외부 스킬·MCP는 설치 전에 보안 검수를 한다.
4. **객관적 검증**: 실제 실행 1회 결과와 로그. 빈 입력·오류 입력 테스트. 크레딧 차감 API는 빈 입력 프로브로 대체한다.
5. **완료 기준**: 정상 경로와 실패 경로가 모두 실행 확인되었다. 운영 방법(실행 명령, 로그 위치)이 문서에 있다.

### 코드 변경

1. **전문가 관점**: 수정 전에 재현한다. 변경 범위를 최소로 한다. 기존 코드 관례를 따른다.
2. **원자료**: 관련 소스 파일, 테스트, 에러 로그, 라이브러리 공식 문서.
3. **방법론·도구**: 프로젝트 lockfile에 맞는 패키지 도구. 탐색이 넓으면 Explore 에이전트. 큰 작업은 다른 에이전트에 맡기고 결과를 재검증.
4. **객관적 검증**: 테스트 실행 결과, 재현 절차 재실행, 필요하면 코드 리뷰 도구나 다른 모델의 교차 검토.
5. **완료 기준**: 재현 케이스가 통과한다. 기존 테스트가 깨지지 않는다.

# 부록 B. 출력 템플릿

각 단계의 출력 형식이다. 항목은 그대로 두고 내용만 이번 요청에 맞게 채운다.

### 1단계: 사전 질문 5개

```markdown
**작업 유형**: <리서치·팩트체크 | 보고서·문서 | 데이터 분석 | 강의안·교육 자료 | 자동화·시스템 설계 | 코드 변경>

1. **전문가 관점**: <요청에 없지만 전문가라면 반드시 할 일 1~3개>
2. **원자료**: <자료 이름> — <위치: 경로·URL·API>
3. **방법론·도구**: <방법과 도구>. 배제: <대안> — <이유>
4. **객관적 검증**: <외부 기준> — <실행할 구체 절차>
5. **완료 기준**: <확인 가능한 조건 2~4개>
```

### 2단계: 다시 쓴 프롬프트

````markdown
```text
[목표] <무엇을, 누구를 위해, 왜>
[산출물] <형식> — 저장: <저장 경로>
[먼저 확인할 원자료]
- <자료 1: 위치>
- <자료 2: 위치>
[방법·도구]
- <단계별 방법과 도구>
[검증 절차]
- <실행할 검증 1>
- <실행할 검증 2>
[완료 기준]
- [ ] <조건 1>
- [ ] <조건 2>
[범위 밖] <하지 않을 일>
```
````

### 3단계: 확인 대기 (해당 시에만)

`--확인`이 있거나 비용·외부 영향이 있으면 다음 한 줄로 멈춘다.

```markdown
위 프롬프트대로 진행할까요? (비용·외부 영향: <유료 API 호출 N회 / 발송 대상 / 게시 위치>)
```

### 4단계: 검증과 보고

```markdown
**결과**: <한두 문장 결론> — <산출물 경로>

**실행한 검증**
- <검증 1>: <실행한 명령·열어 본 파일·대조한 출처> → <결과>
- <검증 2>: ... → <결과>

**완료 기준**
| 기준 | 상태 | 근거 |
|---|---|---|
| <조건 1> | 충족 / 미충족 | <근거> |

**미검증 항목**: <항목> — <이유> (없으면 생략)

**발견 사항**: <범위 밖 제안> (없으면 생략)
```

완료 기준에 미충족이 하나라도 있으면 결과 줄에 "완료"를 쓰지 않고 "부분 완료" 또는 "미완료"로 쓴다.

# 부록 C. 적용 예시

입력: `/깊게 Claude Code 서브에이전트 기능을 기업 교육 강의안 1차시로 정리해줘`

### 1단계

**작업 유형**: 강의안·교육 자료 (보조: 리서치·팩트체크)

1. **전문가 관점**: 수강생이 직접 만들어 보는 실습을 넣는다. 기능이 바뀌는 속도가 빠르므로 문서 확인 날짜를 강의안에 적는다.
2. **원자료**: Claude Code 공식 문서의 subagents 페이지 — docs.claude.com. 기존 강의 자료 — 강의 자료 폴더의 관련 노트.
3. **방법론·도구**: 브라우저로 공식 문서 원문을 직접 읽고, 차시 구성 템플릿으로 정리. 배제: 블로그 요약 글 — 버전이 오래되었을 수 있음.
4. **객관적 검증**: 실습 단계를 현재 설치된 Claude Code에서 직접 실행해 서브에이전트 파일 생성과 호출을 확인. 기능 설명은 공식 문서 문장과 대조.
5. **완료 기준**: 학습 목표 3개, 실습 1개 이상, 소요 시간 합계 = 차시 시간. 실습이 실제로 실행됨. 공식 문서 확인 날짜 기재.

### 2단계

```text
[목표] 기업 실무자가 Claude Code 서브에이전트를 직접 만들고 쓸 수 있게 하는 1차시(60분) 강의안
[산출물] md 강의안 — 저장: 강의 자료 폴더
[먼저 확인할 원자료]
- Claude Code 공식 문서 subagents 페이지 (원문 직접 읽기)
- 기존 Claude Code 강의 노트
[방법·도구]
- 공식 문서에서 정의·파일 위치·호출 방법 추출
- 차시 구성 템플릿으로 도입 10분 / 개념 15분 / 실습 30분 / 정리 5분 구성
```
